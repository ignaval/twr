One conversation for all your coding agents.

You talk to one orchestrator. It starts Claude Code, Codex, Grok Build or any Agent Client Protocol agent, each in its own git worktree, here or on another machine. When a thread finishes, asks a question or wants a permission, it comes back to that same conversation, and you answer there or on its card.

how it works

Say what you want. Hear back when it matters.

Most multi-agent setups give you a tab per agent and leave you to notice which one is waiting. In twr you stay in one conversation, and the hub keeps track of every thread for you.

  1. 01 · you

    Ask the orchestrator

    Type on api, rate limit logins per IP. The orchestrator picks or starts a thread, on the runtime you choose, in a worktree on its own branch.

  2. 02 · the threads

    Agents work in parallel

    Each thread runs its agent's own CLI under your login. Tests and builds queue on the machine's job slots, and a thread's background work wakes it when it ends.

  3. 03 · the hub

    What needs you comes back

    Reports, questions and permission prompts land in the conversation and on the thread's card. Open the card with Enter and press a digit, or just type allow ratelimit.

the desktop

Every workspace and thread in one sidebar.

Threads, on the left, lists your workspaces with the current one's thread cards nested under it. The big pane stays your conversation with the orchestrator, and what you type always goes there until you dive into a thread.

  • WorkspacesEach is its own hub, orchestrator and threads, for a client or a side project. Its card counts what waits on you, ⚠2, and what runs, ●1. A click or Alt-1…9 switches.
  • Cards that say where a thread standsState, what it's doing or what it reported, who runs it and its git line, 3 ahead of dev · 2 behind. The waiting item's options are on the card.
  • A color per threadIts card, name and conversation boxes share one of 30 distinct colors, kept across restarts.
  • Ctrl-B hides it wholeThe view takes every column, with a strip of tabs once you have two workspaces. Ctrl-G switches to the grid, Ctrl-F to focus mode.
  • Enter Enter dives inOn a card, the pane shows that thread's transcript and what you type goes straight to it. Esc brings you back.

on a phone

Answer from your phone, however long the card.

Below 60 columns the TUI turns compact: one screen at a time under a tab bar of Chat, Needs you and Threads, every tab and menu choice two rows tall for a finger. Run it in any phone terminal over SSH or mosh. There is no app to install and no server in between.

  • Threads scrolls through the same workspaces and cards as the desktop sidebar.
  • A card longer than the screen opens with its options under the first lines of text. Tap an option to pick it and again to send it, or press its digit. The rest of the text scrolls above the options, and a tap on ↓ 10 more lines · tap turns a page.
  • /c, /n and /t switch screens where Tab is awkward. A notification command can push to your phone when something needs you.

permissions

It relays your answers. It never makes one up.

The orchestrator can pass on an answer you gave. A short command such as allow both or deny the webapp one answers a permission at once. Anything else, and every answer to a question, goes on a card that only you can confirm, and every answer names the exact revision of the item you saw.

The agents twr runs can read the hub and run jobs for their own thread. They can't answer a permission or a question, change a mode, delete a thread or send prompts. twr is not a sandbox, and the security model says what this guard covers and what it doesn't.

Some runtimes decide a few things themselves. A Codex thread in auto mode has, by default, Codex's own reviewer agent approve or deny a command its sandbox refused; each decision shows in the transcript as an auto_review call. Set [codex] auto = "ask" to get a card instead.

A card's popup answers only what it drew in full and you had time to read, so a key pressed as an item changed answers nothing. Enter on an empty line opens it; 1-9 answer.

features

What else is in the binary.

runtimes · any agent you already use

  • Claude Code, Codex and Grok Build run through their headless modes. Any Agent Client Protocol agent works too, --runtime 'acp:gemini --experimental-acp' for example, and other CLIs get a clearly marked PTY fallback.
  • Move the orchestrator to another runtime mid-conversation, with a handoff. Move a thread to Codex and back to Claude Code and its earlier Claude Code session resumes.
  • Several logins of one runtime, a work and a personal Claude subscription for example, chosen per thread. twr never reads or stores a token. Accounts on remote boxes, balancing and failover aren't supported yet.
  • twr attach opens the agent's own CLI on a thread's session.

runtimes.md · accounts.md

isolation · worktrees and background work

  • Each thread works in its own git worktree, on branch twr/<name>, or in your checkout if you ask.
  • Park a thread to free its worktree and resume it later on the same session. Deleted threads go to a trash you can restore from.
  • Jobs queue on the machine's slots; send --after holds a prompt until another thread finishes. Messages waiting for a thread list above the input box, to edit, delete or send now.
  • A card tells a hung turn from one waiting on its own tests, by what it has in flight.

worktrees.md · jobs

remote boxes · SSH, containers, dial-in

  • After twr box add gpu me@gpu-box the hub installs its own build over SSH (twr box install for a box of another OS or CPU) and starts a box daemon there. Threads keep running across disconnects, hub restarts and laptop sleep, with no token, listener or tunnel to set up.
  • Container boxes through docker exec, podman or kubectl exec, for repositories you don't trust.
  • Dial-in boxes, for a machine the hub can't reach, connect out over wss:// with a token.
  • Linux and Mac boxes; on a Mac the daemon starts where Claude Code can read its keychain login. twr box doctor says what's wrong and how to fix it.

runners.md

memory & context · long-running work

  • The orchestrator keeps notes on your preferences and setup, one memory per workspace, across sessions, restarts and runtime switches. Notes are information, never authority. twr memory manages them.
  • Context compactions show as a line in the conversation. /compact-context compacts a thread between turns, and before a message goes to a Claude Code thread with a large context whose prompt cache has expired, twr asks whether to compact first.
  • A hub with weeks of history starts from a checkpoint instead of replaying its whole log, and old turns' detail moves to an archive.

memory · compaction

in the terminal · the input box

  • A line starting with ! runs a shell command of yours, in the thread's worktree when you're in a dive. !! also hands the output to the thread.
  • Ghost-text suggestions for your next message: Tab takes one, nothing is sent until you press Enter.
  • Shift-Enter for a new line, over mosh and SSH too, after twr terminal-setup. /settings changes the common options and writes back only that line of your config.

tui.md

read aloud · and keeping track

  • /read on reads the orchestrator's replies as they come. On a server over SSH or mosh, twr speak --ssh <server> plays them on your laptop, with nothing on the server's audio.
  • twr usage shows each subscription's 5-hour and weekly windows, and what each thread's turns spent.
  • /decisions opens an audit table of the hub's routing and grading decisions, with the provider that made each one.

read-aloud.md · decisions

what runs where

twr is local. Your agents are not.

twr itself has no account, no cloud service and no telemetry. The agents it runs call their providers under your own logins, so their terms and quotas apply. The hub also asks a small model, with the same logins, for suggestions and summaries until you turn them off.

On machines you run

  • The hub, its append-only SQLite log and the TUI: one Rust binary.
  • Worktrees and jobs, here or on your boxes; cards, the orchestrator's memory and checkpoints.
  • Boxes you add, reached over SSH, a container command or a connection they open.

Model calls, with your logins

  • The orchestrator and every worker: each runtime's CLI, signed in by you.
  • Next-message suggestions and one-line thread summaries, both on by default: the hub asks a small model through Claude Code or Codex. Turn them off in /settings or with [tui] suggest = false and summaries = false.
  • Codex's reviewer, for Codex threads in auto unless you set ask.

What you bring

  • git, and at least one of claude, codex or grok, signed in with its own CLI.
  • For heavy automation, an API key rather than a personal subscription is the safe choice.

install

Three steps to the first thread.

  1. Install twr. The script puts the release build for your machine in ~/.local/bin, without sudo, after checking it against the release's checksums, and their signature where your openssl can verify it. 
    curl -fsSL https://twr.tools/install.sh | sh

    Linux x86_64 and aarch64, macOS on Apple silicon and Intel. Or download an archive from the releases page, or build it with Rust 1.89 or newer: cargo install --locked --git https://github.com/ignaval/twr twr-cli.

  2. Sign in to an agent. twr runs claude (Claude Code 2.1.110 or newer), codex or grok as you; log in with each one's own CLI first.
  3. Open it. The first run asks which agent runs your orchestrator. 
    twr                                  # the TUI; starts the hub
twr thread new ~/code/api --name api # or let the orchestrator start threads
twr update                           # later: the latest release

twr is before 1.0 and has one maintainer: commands, config keys and the socket API may still change between releases. macOS is built and tested in CI but has had less hands-on use than Linux. Windows is unsupported. install.md covers versions, signatures and the installer's options; the changelog lists what each release changed.
