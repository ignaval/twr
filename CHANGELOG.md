# Changelog

All notable changes to twr are recorded here. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and twr follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html): before 1.0, a new minor version may change commands, config keys and the socket API.

## [Unreleased]

### Added

- SSH boxes: a box the hub reaches over SSH needs no token, listener, tunnel or service. `twr box add gpu me@gpu-box` probes the box in your terminal, asks, writes `[boxes.gpu]` with `transport = "ssh"` to `boxes.toml` (next to `config.toml`, which twr never edits) and adds the box to the running hub. The hub installs its own twr build on the box (`~/.local/share/twr/runner/builds/<build id>/`), connects over ssh without prompting and with forwarding off, and starts a box daemon there that runs the box's threads and keeps them running across disconnects, hub restarts and laptop sleep. The hub and the daemon talk through a channel only the hub's key opens (Ed25519-signed X25519, ChaCha20-Poly1305). When the hub runs a new build of the same protocol, the box switches to it once it has been quiet for 2 minutes, without losing a session or a prompt. A build of another protocol that the hub can't drain (below) replaces twr on the box at once: the box's running turns are cut, but its agents are recorded as stopped for the switch, not crashed (no crash card, queued prompts kept), and each thread's next prompt resumes its session. See [runners.md](docs/runners.md#ssh-boxes).
- `twr box list`, `twr box status <box>`, `twr box install <box>` (a release's build for a box of another OS or CPU, its signature checked as `twr update` checks one, or `--binary <path>`) and `twr box remove <box>`.
- `hub.info` (`twr info --json`) has the hub's `build` id, and for each box its `transport`, `state`, and for an SSH box its last error, notes, OS and CPU, the build launched there, the build its daemon runs and whether a switch is pending.
- Agents on boxes: each box tells the hub which agent CLIs it has (`claude`, `codex`, `grok`), at which version, and whether each is logged in, without passing on any account detail. `twr box list` gets an AGENTS column (`claude ✓ codex ✗ grok ?`), `twr box status` each agent's path, version and login, and `hub.info` each box's `agents` (top-level `agents`: the hub's own machine). A thread started on a box that reports its CLI missing gets a warning. A new socket method, `box.agents {box, refresh?}`, has the box probe them again. See [runners.md](docs/runners.md#agents-on-a-box).
- The login shell's `PATH` on boxes: a runner (`twr runner`, or an SSH box's daemon) asks your login shell for its `PATH` once as it starts and puts it before its own for the agents it runs, so an agent in `~/.local/bin` or an npm folder is found when ssh, systemd or cron started the runner. `sh`, `bash`, `zsh`, `ksh` and `fish` are asked; `csh` and `tcsh` are not. See [runners.md](docs/runners.md#the-login-shells-path).
- `twr box doctor <box> [--json]` says what is wrong with a box and how to fix it, with or without a hub and with the box offline: the hub's view, ssh with and without prompting, the box's builds, its daemon, logind, its agents, git, free disk and its projects' repositories. See [runners.md](docs/runners.md#check-a-box).
- `twr box login <box> <agent>` starts `claude`'s, `codex`'s or `grok`'s own login on a box, in your terminal, over ssh with forwarding off. twr never runs a login by itself and never sees what you type. See [runners.md](docs/runners.md#log-an-agent-in-on-a-box).
- `twr box project <box> <project>` finds a project's repository on a box and records where it is (`[boxes.<box>.projects.<project>] repo`, in `boxes.toml`), so `twr thread new <project> --box <box>` uses it. The box's twr build looks at the path the repository has under your home, under the box's home, then under the box's `~/code`, `~/src` and the other default project folders, and compares each repository's `origin` with the hub repository's (credentials left out, never sent). It records one only after asking (or with `--yes`), and only when exactly one matches and the search was complete; otherwise it lists them, and `--path <path>` records the one you pick. `--clone` runs `git clone` of the project's origin on the box, in your terminal, with the box's own git credentials and forwarding off (no `file://`, local paths or URLs with credentials), and records the clone; twr never fetches (Git LFS files stay pointers until you run `git lfs pull` there). A clone stopped by Ctrl-C, a dropped connection or a failure removes the folder it made. A running hub takes the change at once (a new socket method, `box.projects {box}`). `twr box add` names the command for each project configured for the new box, and a thread on a box that doesn't have its project says to run it. See [runners.md](docs/runners.md#projects-on-a-box).
- The TUI shows a thread's remote box where the thread is: `codex@gpu` on its card, tile and dive header, with what is wrong when the box isn't simply online (`@gpu offline`, `reconnecting`, `switching`, `update pending`, `needs install`, `twr mismatch`, `error`), on the compact Threads screen too. It asks the hub every 10 seconds and shows a runner connecting or leaving at once. Tiles no longer say `@local`. See [tui.md](docs/tui.md#stack-view).
- The orchestrator's `spawn_thread` takes a `box`, and `hub_info` shows it each box's state and agents (not its ssh destination, notes or paths). It starts a thread on another box when you ask for one. See [orchestrator.md](docs/orchestrator.md#what-it-may-and-may-not-do).
- Mac boxes: on a Mac, the relay starts the box daemon as a launchd job in the GUI session of whoever is logged in at the Mac's screen, where Claude Code can read its keychain login; from ssh it can't. With no one logged in there, it starts the daemon from ssh and says so. The job gets an allowlist of the ssh session's environment only, so an API key there doesn't reach it. `twr box add` says what a Mac needs, `twr box doctor` checks it in a macOS group (a GUI session, how the daemon was started, Claude Code's login as the daemon sees it), and `twr box login` and `twr attach` say when the keychain may be out of reach. `TWR_BOX_LAUNCHER=launchd` forces the launchd start. See [runners.md](docs/runners.md#mac-boxes).
- `twr box restart <box>` has the hub restart a box's daemon (`box.restart`): it ends its connection, the relay stops the daemon and starts a new one, and the command waits for the box to come back and says how the new daemon was started. `hub.info` shows each box's connection `epoch`, and for an SSH box `restart_pending` and how its daemon was started (`launch`), which `twr box status` shows too. A restart may take minutes when the daemon finishes a repository change first: the relay says how it goes, and the command prints those notes. See [runners.md](docs/runners.md#restart-the-box-daemon).
- `twr box install <box> --from-box <path>` installs a twr that is already on the box, such as one built there with `docs/tools/dev-install.sh`, with the same checks as an upload.
- Container boxes: `transport = "command"` with `command = ["docker", "exec", "-i", "<container>"]` (podman, `kubectl exec` and the like too) has the hub reach a box through that command instead of ssh, with the same build install, box daemon and sealed channel, so agents working on a repository you don't trust can't reach your files, your ssh-agent or the hub's socket. `twr box add <name> --command docker exec -i <container>` adds one, checking that the command passes its input and gives the box no terminal. `terminal_command` is used by `twr box login` and `twr box project --clone`; `twr attach` is refused on a container box for now. twr never creates or removes the container: `docs/tools/container-box/Dockerfile` and the recipe in the docs set one up. A `boxes.toml` with a command box doesn't load in an older twr. See [runners.md](docs/runners.md#container-boxes).

- Dial-in boxes: a box the hub can't reach over SSH, set up by twr instead of by hand. `twr box add gpu --dial-in --hub wss://hub.tail1234.ts.net:7878` writes a token box with a new token to `boxes.toml`, adds it to the running hub and prints the one command to run on the box, and the token only on a terminal; it refuses without `[hub] listen` and takes only `wss://` or `ws://` to a loopback address (an ssh tunnel's end). `twr runner install-token gpu` on the box reads the token at a prompt that does not show it (or from a pipe), stores it in `~/.config/twr/runner-tokens/gpu.token` (mode 0600), and prints the run command and a systemd user unit or a Mac LaunchAgent to paste. `twr runner` reads that file by default, and reads its token file again after a refusal, so a new token is picked up without a restart. See [runners.md](docs/runners.md#dial-in-boxes).
- `twr box token <box>` prints a token box's token, `--rotate` replaces it, and `--reload` has the running hub read it again. The hub takes a token box's token live (a new socket method, `box.token {box}`, users only): a rotated or removed token stops working at once and the box's connection drops, with no hub restart. `twr box remove` of a token box revokes it that way and says how to stop the runner on the box. `hub.info` says whether the hub's runner listener is up (`listening`).
- `twr box doctor` on a dial-in box checks the listener, the box's token and its agents as its runner sees them, with fixes to run on the box; `twr box project --path` records a path on a dial-in box without looking; `twr box install`, `restart` and `login` say what to run on the box.
- A hub update that changes the runner protocol no longer cuts the turns running on a box when the hub can still drain the box's older twr (protocol 6, for this hub's 7; `hub.info` `drainable_protocols`). The hub serves the old daemon drain-only: running turns finish and stream (up to 30 minutes), their permission requests and questions can still be answered, and prompts wait. Then it stops the box's agents for the upgrade (no crash card), replaces twr on the box and runs the queued prompts; each thread's next prompt resumes its session. A token runner of the older protocol is drained the same way, then stays connected until you update it. `twr box status` shows the drain (`hub.info` `drain`: stage, since, until) and what to do, `twr box doctor` says a daemon will be drained, and `twr box restart` cuts a drain short without crashing anything. See [runners.md](docs/runners.md#a-new-twr-build).

### Changed

- TUI cards and grid tiles have one section about the thread's status, up to 4 rows: its state and grade, then what it is doing or what came of it, without saying anything twice (`failed · turn 2 failed: rate limited`, `background (1 bg) · cargo test`, `done ✓ · <the report>`). Its first row always shows: a working thread with a stalled notice or a review open still says what it does above the item, and a long item no longer pushes the state off the card. Who runs the thread (runtime, box and model) is in the card's title, before its permission mode; the git state is its last row. See [tui.md](docs/tui.md#stack-view).
- The git line says how far a thread's branch is from its base in words, `3 ahead of dev · 2 behind` (`+3/−2 vs dev` on a narrow card), and shows no numbers when the branch is even with its base or that isn't known. It no longer shows `↑0 ↓0` for a branch without an upstream. See [tui.md](docs/tui.md#the-git-line).
- The main pane has no border: the header band is where it starts and turns yellow while the pane is selected, saying so at its right, and `↓ 12 lines below` is on its last row while it is scrolled up.
- The compact layout's Threads screen shows the threads' cards instead of a line each, scrolled like the column of cards. Its screens are switched from a tab bar, 2 or 3 rows tall where the screen has the rows, each tab a third of the width to tap. See [tui.md](docs/tui.md#on-a-phone).
- `twr attach` to a thread on a remote box runs ssh with every kind of forwarding off (`-a -x -k`, no ports, tunnel or local command), whatever your `~/.ssh/config` says: an attached agent CLI can't use your ssh agent. A box's `ssh` setting may no longer hold options that forward something or change how ssh runs (`-A`, `-X`, `-L`, `-t`, `-o ForwardAgent=yes`, `-o ControlMaster=...` and the like; [configuration.md](docs/configuration.md#notes-on-some-keys)): the hub refuses to start with one.
- A runner reports twr's whole version, with the commit of a development build (`0.2.0+dev.<commit>`), and `twr info` shows each box's version. While a box is offline, `twr info` (and `hub.info`'s `refused`) also shows the latest connection naming it that the hub refused, and why: a runner of another protocol, one that didn't accept the hub's proof (its token differs), or a bad proof.
- A runner the hub refuses, or whose hub can't prove it knows the token, waits at least a minute before it tries again, and a protocol refusal is logged as an error saying to run the same twr on both sides.
- The runner protocol is now version 7 (the agents op). An SSH box of the hub's OS and CPU switches to the new build by itself; a box of another OS or CPU shows `needs_install` until `twr box install <box>`; update every token runner (`twr runner` on a box you set up yourself) together with the hub, or the hub refuses it.

### Fixed

- A TUI left open across an upgrade (`twr update`, the installer, `dev-install.sh`) starts the new build when it opens a workspace whose hub isn't running. On Linux it used to fail with `workspace NAME: starting the hub: No such file or directory`, because it tried to start the file the upgrade had replaced. If twr was removed rather than replaced, the error now says so and to reopen the TUI. See [usage.md](docs/usage.md#stop-the-hub-and-update-twr).
- A call on a connection the hub closed says so (`the hub closed the connection before thread.send reached it (nothing was done): the hub is stopping`, then to check with `twr info`) instead of `writing request to hub: Broken pipe`. A hub that stops tells the connections it closes why, and a request it can't read (malformed, or over 16 MiB) is refused with its reason, which clients used to skip. The TUI and the MCP server reconnect after their hub stopped or restarted. A call the old hub never got is sent once on the new connection; a `thread.send` the hub may have acted on is never sent twice.

- `twr thread new <name> --box <box>` sends `<name>` to the hub as typed for a remote box. It used to turn a name that is also a folder in the current directory into that folder's path on this machine, so a project configured only for the box (`[boxes.<box>.projects.<name>]`) wasn't found.
- Box daemons on macOS: a `twr box project --clone` reserves and cleans up its folder through held directory descriptors, as on Linux, instead of `/proc` paths a Mac doesn't have, so a folder swapped for a link meanwhile can't redirect the cleanup. Where a process group is ended after its leader exits (probes, ssh, `git clone`), what `waitid` reports of the leader is no longer trusted on macOS, which doesn't fill it in reliably: the exit status is the reap's, and a clone's group is killed even after a success (fail closed). A process that something else reaped first is never signalled again.
- Jobs, headless runtimes, notification commands, the hub's ssh, the git twr runs and the tools twr runs in the background start in a session of their own, without a controlling terminal (a `pty:` runtime's is its own pseudo-terminal), and the hub `twr` starts has none either. A job or runtime that read the terminal of the shell that started the hub (a prompt, `stty`) was stopped by it for good; it now gets an error. `twr job cancel` still ends a job's whole process group.
- `twr runner` and an SSH box's daemon stop cleanly on a SIGTERM or SIGINT that comes while they start (opening the box can take seconds): they exit 0 before they connect or bind their socket, instead of being killed by the signal.
- A box relay whose hub went away while it waited for the box daemon to settle, stop, start or answer no longer goes on to start or replace the daemon: it ends, starting or stopping nothing more (a start already under way finishes).
- The hub's warning about a config file other users can access names the file that holds the secret: a token in `boxes.toml` no longer blames `config.toml`, and a `boxes.toml` holding a token is checked too.
- A token box removed from `boxes.toml` was still accepted, with its old token, until the hub restarted; `twr box remove` now has the running hub stop accepting it at once.
- An error reading the config files that the hub returns (`box.add`, `box.projects`, `box.token`) or logs no longer quotes the offending line, which may hold a token.
- The `box.projects` errors for a box no longer in the files, or whose settings changed, read without runs of spaces.

## [0.2.0] - 2026-10-15

The first public release. twr is one conversation for all your coding agents: you talk to one orchestrator, and a local hub runs the threads it starts, Claude Code, Codex, Grok Build or any Agent Client Protocol agent, each in its own git worktree. Permissions, questions and reports come back to that conversation or to the thread's card, and only you answer them. It's a single binary for Linux and macOS, with no account, cloud service or telemetry. Earlier versions were never published.

macOS is built and tested in CI on every change, but it has had less hands-on use than Linux so far: please [report](https://github.com/ignaval/twr/issues) what breaks there.

### Security

- Agent `twr` calls are no longer all read-only. A thread's agent can start and cancel [jobs](docs/usage.md#jobs) for its own thread, and a job runs outside the runtime's sandbox. An agent may now start one only while its thread's mode may run commands (`manual` or wider): `twr job run` from an agent is refused in `plan`, `dontAsk`, `read-only` and in a runtime's own mode that twr can't classify. Review any allow rule you wrote when agent `twr` calls only read, such as Claude Code's `Bash(twr:*)`.
- A job records who started it: `user:<client>`, `agent:<thread id>` or `attach:<thread id>`. An agent's job was recorded as the user's.
- A socket client the hub can't identify (its credentials can't be read, or name a process the hub can't see, such as one in another PID namespace) counts as an agent of no thread, no longer as you.
- The runner protocol (version 6) authenticates both sides with a challenge-response over the box token, and the token never crosses the connection. The runner checks the hub's proof before it sends anything else, so a process squatting on the runner's loopback port (an `ssh -R` forward that failed to bind) gets nothing and can't drive the box. Update the hub and every runner together: each refuses the other's older protocol. Start tunnels with `ssh -o ExitOnForwardFailure=yes`.
- The runner listener gives an unauthenticated connection one 15-second deadline for every handshake step together and holds at most 4 of them per address that isn't loopback. It bounds what it buffers to send any connection, so a peer flooding WebSocket pings can't grow the hub's memory, and WebSocket pings no longer keep a silent runner connected.
- The hub refuses a runner frame for another box's thread even when it is a replay, closes a connection that sends a frame with `rseq` 0, and never reacts again to a turn end it recorded itself, so a replayed `turn.ended` can't release a queue a crash holds. A box's trash listing can't stand for another box's items, and a restore brings back only a thread of the box that holds the item.
- A second `twr runner` of a box on the same machine refuses to start, whatever its `--data-dir` and whether it was started from a login session, a service or cron (the lock is in `~/.local/state/twr/runner-locks/`). A restarted runner that can't show a leftover runtime gone (it survived the kill, its process can't be identified, a process tied to it hides its environment, or the process table can't be read) records no exit for it and doesn't start, so the hub never starts a runtime next to it. The runner opens its token file without blocking, so a FIFO there can't hang it.
- `twr runner` refuses plain `ws://` to a host that isn't loopback (`localhost`, `127.0.0.0/8`, `[::1]`, IPv4-mapped loopback) unless given `--allow-insecure`: events and commands would cross the network in clear text.
- Box tokens shorter than 16 characters keep the hub from starting, and the runner refuses them; tokens shorter than 32 get a warning. `twr runner token` prints a new 64-character token. After upgrading, replace a short token in `config.toml` and in the runner's token file, then restart the hub and the runner. An empty `token` is now a config error.
- The hub warns, in its log and in `twr info`, when a `config.toml` holding a box token or a `[notify]` command can be accessed by other users. The runner refuses a token file other users can access.
- Every client checks that the process listening on the hub's socket runs as its own user, and refuses it otherwise.
- The hub refuses to start with a data directory another user owns, or one it can't restrict to 0700; it used to log a warning and go on. It also refuses a socket directory another user owns (root aside) or one every user may write to without the sticky bit, and warns about one its group may write to. Every directory on the way to the data and socket directories is held to the same rules.
- A socket connection holds at most 16 subscriptions at once, and the hub serves at most 1024, at most 256 of them to agents' connections, so an agent can't grow the hub's memory by subscribing again and again.
- An agent's `job.start` and `job.cancel` are checked against the process that asks at each request: a process that left its runtime or attached CLI (its parent exited), or outlived them, still reads but no longer starts or cancels jobs on the connection it opened under them. What is left of an attach can't start jobs on a stopped thread, and an agent's job no longer wakes a stopped thread when it ends.
- An agent's job checks the thread's mode again when it leaves the queue: one queued before the mode narrowed ends as `failed_to_start` instead of running.
- The hub records a job's process group before the job's command runs; a job whose process's start time can't be read doesn't run. After a crash, the next hub kills what is left of that group before it records the job lost, also processes that cleared `TWR_AGENT` from their environment. A job it can't verify gone stays unrecorded, and its thread starts no runtime or job until a later start verifies it. A lost job's end and the prompt that tells its thread are recorded together.
- A socket client the hub fails to classify because of a failure inside the hub counts as an agent, no longer as you.
- `job.log` and a job's wake prompt keep to 64 KiB of text for output that isn't UTF-8 too.
- twr's own git calls override a repository's `diff.external` like its other drivers, and after each command that could run a driver twr lists the repository's config again. A driver named while the command ran is logged as an error, and a snapshot or merge-readiness check that raced is discarded.
- Git LFS, a filter of your own config, no longer runs a program the repository's config names (a custom transfer agent, an extension, a credential helper, an ssh command or askpass): where a repository's own config names one, twr's checkouts of it hold LFS files as pointers, and the hub logs why.
- Debug builds trust the test token (`TWR_TEST_USER_TOKEN_FILE`) only from a regular file the hub's user owns with no group or other access, and a hub started by the CLI no longer inherits the variable. Release builds never send or trust it.
- The orchestrator's project reads refuse a repository whose object storage holds a symbolic link (its objects folder, a loose object's folder or file, a pack), checked, with its other redirects (alternates, `commondir`, a git directory outside the repository), before and after each read: such a link could have it read another repository's committed files, a protected one's included, under an allowed project's name.
- A project search no longer says through `more` whether a file it refuses to show matched: it searches again without the files a read refuses. A search covering a file whose name isn't UTF-8 and that a read would refuse (a secret, or a binary file) is refused, whatever it looks for.
- `context.set` writes `.twr/context.md` relative to the `.twr/` directory it checked, held open: a `.twr/` swapped for a symbolic link meanwhile is never written through, and the write fails.
- A thread restored from the trash at another path (its old one taken, or under `--as`) has its submodules, nested ones too, connected to their repositories' copies in its new git record. They named the old record, which another worktree may have taken since. A restore that can't copy or connect them all fails and removes what it made.
- A merge readiness check that fails no longer keeps the last result on the card and in `get_thread`: readiness is unknown until a check succeeds.
- The disk measurement of a worktree reads a directory's entries as it counts them, so its 2,000,000-entry limit also bounds what one huge directory makes the hub read and hold.
- With `[threads] cpu_weight` or `memory_high` set, the hub keeps `systemd-run`, `systemctl`, `nice` and `env` by their full paths even when a relative `PATH` entry found them. A worker started its wrapper from its own worktree, where the relative path could name a file of the repository's, run without the limits.
- `twr trim` escapes control characters in a thread name it couldn't find, as the rest of the CLI's output does.
- `twr update` reads a `file://` mirror's files only when they are regular files, at most 1 MiB each and within 60 seconds: a FIFO or a device there no longer hangs it or fills its memory.
- Releases are signed. Each release's `sha256sums.txt` and `install.sh` carry Ed25519 signatures. `sha256sums.txt` names its release and lists `install.sh` too. `twr update` picks one release on GitHub and, before running anything, verifies both signatures with the key built into twr and checks that the checksums are that release's and list its installer. `install.sh` verifies the checksums' signature wherever `openssl` can check Ed25519, refuses checksums of another release than the one asked for, and downloads with curl over HTTPS only. See [docs/install.md](docs/install.md#checking-the-signature).
- A narrower permission mode (`twr mode`, or a move to a runtime whose mode allows less) no longer waits for the runtime's own background tasks, or for a request one of them raised between turns, before it restarts the runtime: while they ran, the runtime could keep starting turns of its own in the old mode. The runtime restarts right away, or after its current turn, its background tasks end with it, and their open requests are closed as by a stop; `twr mode` says so. Narrower means anything the runtime may do without asking is lost, such as Codex `on-request` to `manual`, or `auto` to `never`; Codex `auto` to `bypassPermissions` is a widening. A change that keeps or widens the mode still waits.
- After a runtime crash that fails a turn and gets no automatic retry, queued prompts wait for you again, until you send a prompt or resume the thread: the hub's once-a-second background check dispatched the next queued prompt about a second after the crash, and a runner box reconnecting dispatched its queue too. The hold now survives a hub restart (a runtime that died with the hub itself still lets the queue go on), and so does your release: a prompt you sent after the crash, while the thread's box was offline, still goes out when the box reconnects after a hub restart. Only your own send or resume releases it, or your Send on the card of a prompt that waited: a job's wake, a lost job's notice, a prompt that waited for other threads (`--after`) as they finish, and the orchestrator's send or resume no longer do. The same holds for a queue held after a runtime failed to start or a remote box failed a send.
- Codex: every mode with a workspace-write sandbox (`manual`, `on-request`, `acceptEdits`, `never`) now overrides `[sandbox_workspace_write] network_access` and `writable_roots` (no network, no extra roots), which Codex otherwise took from your Codex config or a project's `.codex/config.toml`. `auto` always sends its own roots, even an empty list. A session whose sandbox still reports network access or a writable root twr didn't ask for is ended before any prompt.
- Codex `auto`: the worktree's git metadata is made writable only as found from the repository the thread was made from, and only the record git keeps for that worktree, never another worktree's. An agent that rewrote its worktree's `.git` file or its git dir's `commondir` (both writable in `auto`) could make its next start grant writes elsewhere, such as the home directory through a link.
- ACP agents: an agent that switches itself to a wider mode during a prompt, without a plan-exit you allowed, has the prompt cancelled and the session ended, instead of the prompt running on in that mode until the agent answered twr's switch back. Mode updates that name another session, or none, no longer count, also while a session opens (a `plan` thread could otherwise start on another session's report).
- Permission cards show a command as it runs: newlines show as `⏎` (tabs `⇥`; anything but printable ASCII, the space and letters and digits, such as a space at either end, other whitespace, invisible characters and symbols, as `⟨U+XXXX⟩`), and whitespace is no longer collapsed or trimmed, nor dropped where the TUI wraps a permission. A line break after a `#` comment made the next command look like part of the comment. A Codex grant's directory is shown the same way. A command cut on the card says so, with how much is left, and the TUI's request popup and `twr respond` show all of it (`input:`); one over 64 KiB can only be denied. A long harmless prefix could push the command that would run off the card.
- A Claude Code permission card also shows the request's other fields after the command, between `⟦ ⟧`, such as a Bash call's `dangerouslyDisableSandbox` or `run_in_background`, or a Write's content (a Bash call's description and timeout are left out): the card showed only the command, so allowing it could also turn the sandbox off unseen. A request whose fields together exceed 64 KiB, such as a Write of a large file in a mode that asks, can only be denied. Tool names and ACP kinds on a card are marked like the command.
- An ACP agent's permission request with no title shows its whole input, marked like a command, instead of a shortened line with whitespace collapsed.
- A lone answer to the orchestrator ("yes", "ok", "allow it") no longer applies at once, even with one request waiting: you may be answering the orchestrator's own question. It reaches the orchestrator, and a relay of it goes on the confirm card, which names the request. "allow api" still applies at once.
- A word that one thread has as its name and another as a name part or former name (`api` beside `x-api-y`) names neither in a short command. A short command naming, or able to name, a thread made or renamed after what your screen showed goes on the confirm card: the orchestrator makes and renames threads without asking.
- The orchestrator starts a thread outside your configured projects only inside a git repository, and never in one that is or holds your home folder, or holds or is inside twr's data directory, `TWR_HOME` or a credentials folder (`~/.ssh`, `~/.config`, ...). You still can.
- A Claude Code orchestrator, and `twr attach` of it, run with Claude Code's attachments off (`CLAUDE_CODE_DISABLE_ATTACHMENTS=1`): an `@<path>` in a hub notice quoting a worker could otherwise have Claude Code read that file into the orchestrator's context, with no tool call for its file guard to see.
- A Codex orchestrator gets twr's MCP server and no other: Codex adds the servers a thread is given to those of your Codex config, so the adapter reads the config first and turns the others off by name, turns plugins and apps off, and ends the session if another server starts anyway.
- Only a Claude Code orchestrator can be attached. `codex resume` would load your Codex config's MCP servers and plugins, and grok's interactive CLI takes no tool profile, so attaching a Codex or Grok Build orchestrator is refused like an ACP one. `codex resume` keeps the built-in tools a thread turned off.
- The orchestrator's move of a thread to another runtime goes on the confirm card unless the thread is in `plan`, `read-only` or `dontAsk`: runtimes differ in what one mode lets through, so a move could let the thread do more without asking. A mode change on a confirm card applies only on the runtime (and ACP agent) the thread ran when the orchestrator proposed it: Confirm skips it, saying so, for a thread moved since, where the same mode could let the other runtime do more without asking.
- `twr attach` refuses a session id that isn't one twr passes to a command line (letters, digits, `.`, `_`, `:`, `-`, not starting with `-`), for every runtime: a runner reports its threads' session ids, and `--dangerously-skip-permissions` as one would be an option of `claude --resume`.

### Changed

- Idle trims (`trim_idle_after`) delete less: only entries with a path component named by both `park_disposable` and the new `[threads] idle_trim_disposable` (also per project), which defaults to `target/`, `node_modules/`, `__pycache__/`, `.pytest_cache/`, `.mypy_cache/`, `.tox/`, `.gradle/` and `.next/`. `dist/`, `build/`, `.cache/`, `.venv/` and `coverage/` stay. `twr trim` and the disk card's Trim are unchanged.
- Trimming, and deleting a thread's build output instead of keeping it in the trash, work on macOS too.
- `twr update` downloads the installer and the checksums from the GitHub release instead of running the installer twr.tools serves.

### Added

### Fixed

- `install.sh` refuses a new binary whose `--version` prints a version and then fails, keeping the installed `twr`, as it did for one that doesn't run at all.
- The notification hook sees its command exit even when a process the command left running holds its stdin unread, and ends that process then instead of at `timeout_secs`. A report rewritten after its notification no longer notifies again once the hub has restarted.
- `twr wait` counts a prompt held with `--after` as work to come after a failed turn too, instead of reporting the failure while that prompt is still to run.
- A prompt held with `--after` for a thread that finished its turn and was then parked or stopped goes out (or gets its card) at once, also when that thread has prompts of its own held for other threads. Before, it waited forever.
