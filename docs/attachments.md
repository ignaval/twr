# Thread attachments

Desktop and mobile use the shared upload controller. Selecting a file starts a bounded upload; the composer shows image or text previews, progress, Pause, Resume, and Cancel. Completion adds the resulting path to that thread's draft. Sending the message is always an explicit user action. Navigating threads preserves the queue while the app remains open.

Each file is limited to 25 MiB. Image previews accept PNG, JPEG, GIF, WebP, and AVIF up to 10 MiB; text previews read at most 64 KiB and render as plain text. Object URLs are released when an attachment is dismissed or the controller is disposed. The UI keeps at most eight attachment previews and uploads two concurrently. Completed previews are dismissed after their draft is sent or evicted when room is needed for new files.

The gateway accepts `upload-begin`, `upload-status`, `upload-chunk`, `upload-commit`, and `upload-cancel` only for devices with operate permission. Local desktop uses a separate trusted-renderer IPC lane with a strict method allowlist, 64 KiB chunks, workspace validation, and a captured companion bridge. All commands resolve the destination through the authenticated hub's `thread.upload` RPC. The hub supplies the recorded thread worktree, or the registered repository when a thread has no separate worktree, and the authenticated caller scope. Registered repository aliases are resolved on the destination host; managed worktree paths stay strict. A thread on another box forwards the same request through runner protocol 8's `upload` operation over the authenticated runner connection. Runner protocols 7 and 6 can drain existing sessions, but cannot accept new uploads.

A transfer ID is bound to the authenticated device, workspace, thread, full-file SHA-256, and working directory. Every chunk includes its exact expected offset. Resume queries the server's received byte count and SHA-256 of that prefix, then verifies the original local file before continuing. Lost begin, chunk, and commit acknowledgements can be recovered without sending duplicate bytes. A changed destination or mismatching prefix is refused.

Uploads are staged under `.twr-uploads/<random-directory>/<filename>.part` using directory descriptors, exclusive creation, and `O_NOFOLLOW`. Directory traversal, symlink roots or ancestors, symlink upload directories, and changed worktree roots are refused. A generated `.twr-uploads/.gitignore` keeps staged and committed attachments out of git status. A commit checks the declared size, transport SHA-256, and actual disk bytes; verifies that staging directories and the staged file still match their pinned descriptors; syncs the file; and atomically renames it. Upload requests never send prompts or inject bytes into terminals.

The gateway retains its 128 MiB per-device quota over ten minutes, with a minimum charge of 64 KiB per file, including empty files. Each box also enforces that quota for its authenticated caller, limits pending transfers to four per caller and 32 per box, and bounds retained receipts. Cancellation refunds an unfinished reservation and removes its staged file; a committed attachment retains its quota charge and cancellation does not remove the file. Idle transfers and receipts expire after 15 minutes, with periodic cleanup. Pending transfers survive transport reconnects while the gateway, hub, and runner processes remain alive; process restarts discard pending transfer state. The original `File` stays only in application memory, so closing the app requires selecting it again.

Uploads use a bounded lane separate from approvals and other device commands. Client upload calls time out after 15 seconds, gateway requests after 12 seconds and remote runner requests after 10 seconds. After a dropped connection, use Resume to verify the received prefix and continue; the app does not send the file again automatically. An operation already in progress is polled through status. Cancelling a committed transfer reports that its file is kept rather than claiming to delete it. Queued files retain their original workspace and wait while you use another workspace.

Uploaded copies are disposable during explicit park, delete, or manual trim worktree cleanup. Keep an original outside the worktree when you need it later; a captured or generated file may otherwise exist only in the app's memory. Automatic idle trimming does not remove attachments. Configure `park_disposable` if you want different explicit cleanup behavior.

Runner upload commands use four dedicated execution slots and keep their idempotent transfer receipts in the upload manager. Per-chunk results are not added to the runner's ordinary durable command-result spool. File creation, chunk reads/writes, checksum commits, and expired-file cleanup run outside the global upload manager lock.
