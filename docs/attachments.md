# Thread attachments

Desktop and mobile use the shared upload controller. The paperclip in the message box picks files and starts a bounded upload for the conversation on screen (the orchestrator's, or a thread's). Each file shows inside the message box, above the text: an image as a 64-pixel tile of its preview, any other file as a chip with its kind's icon, its name (cut short, the whole name in its tooltip) and its size. Neither shows where the file was uploaded, and nothing is written into the draft. While a file uploads, the tile's bottom strip or the chip says how far, in percent. The ✕ at its top right cancels the upload, or removes an uploaded file. A failed upload shows a retry button, whose tooltip and description are the error; a paused one shows a resume button. Otherwise clicking the tile or chip opens the file in a dialog: a larger image, a text file's first 64 KiB as plain text, and Pause, Resume and Remove. Attached files belong to their conversation and stay there while you switch threads or workspaces. The orchestrator's stay with the orchestrator when a switch of its model or effort gives it a new thread: a file still waiting to upload goes to the new thread, and one whose upload has begun finishes into the old one, which uploads to the same directory.

Sending a message names the conversation's uploaded files after its text, one pair of lines per file:

```text
Uploaded file: <name>
<path of the uploaded copy>
```

so the orchestrator and workers get the paths, then clears them from the box once the message is accepted: sent, queued behind a running turn, or saved on this device until the hub reconnects (the saved copy holds the same lines). A name keeps to its one line: line breaks and other control characters in it become spaces. Send works with files and no text. While a file is still uploading, paused or failed, Send is disabled and a line under the files says why; resume or remove the file to send. A composer command (`/…`) or a shell line (`!…`) takes no files: they stay for the next message. Send as implementation loop makes them part of the loop's task. A hands-free voice message to the orchestrator takes the orchestrator's uploaded files; a file still uploading waits for a later message. A file goes with one message only: a message reserves its files as you send it, so a typed message and a hands-free one sent at the same moment can't both name the same file, and a message that is not delivered gives them back. Taking a queued or saved message back to the draft (Take back, Move to original draft, a message the hub holds for a waiting request) puts its text in the draft and its files back in the box, uploaded. The names and paths of a conversation's uploaded files are saved on this device with its draft (encrypted, as drafts are), so they are back in the box after the app restarts, with or without text; a file whose upload had not finished must be picked again. **Reset offline storage…** in Settings empties the box's files with the drafts, so none of their names or paths is saved again. Sending a message is always an explicit user action.

In the conversation, the queue and the outbox, a message's `Uploaded file:` pairs show as chips with the file's name only (an image with its preview while the app still holds it; nothing is downloaded). Only that exact form counts: an `Uploaded file: <name>` line followed by a line that is an absolute path. Other text is shown as written. Copy message copies the text as sent, paths included.

Each file is limited to 25 MiB. Image previews accept PNG, JPEG, GIF, WebP, and AVIF up to 10 MiB; text previews read at most 64 KiB and render as plain text. Object URLs are released when an attachment is removed or the controller is disposed; the app keeps the previews of the last 16 sent images for their messages' chips. A conversation holds at most eight files, at most eight uploads are unfinished at once, and two upload concurrently. A file waiting for its message is never dropped to make room.

The gateway accepts `upload-begin`, `upload-status`, `upload-chunk`, `upload-commit`, and `upload-cancel` only for devices with operate permission. Local desktop uses a separate trusted-renderer IPC lane with a strict method allowlist, 64 KiB chunks, workspace validation, and a captured companion bridge. All commands resolve the destination through the authenticated hub's `thread.upload` RPC. The hub supplies the recorded thread worktree, or the registered repository when a thread has no separate worktree, and the authenticated caller scope. Files attached in the orchestrator's conversation go to the orchestrator's working directory (`orchestrator.cwd`, your home folder by default), under its `.twr-uploads` folder; the orchestrator's own file tools are confined, so it passes such a path on to a worker rather than reading the file itself. Registered repository aliases are resolved on the destination host; managed worktree paths stay strict. A thread on another box forwards the same request through runner protocol 8's `upload` operation over the authenticated runner connection. Runner protocols 7 and 6 can drain existing sessions, but cannot accept new uploads.

A transfer ID is bound to the authenticated device, workspace, thread, full-file SHA-256, and working directory. Every chunk includes its exact expected offset. Resume queries the server's received byte count and SHA-256 of that prefix, then verifies the original local file before continuing. Lost begin, chunk, and commit acknowledgements can be recovered without sending duplicate bytes. A changed destination or mismatching prefix is refused.

Uploads are staged under `.twr-uploads/<random-directory>/<filename>.part` using directory descriptors, exclusive creation, and `O_NOFOLLOW`. Directory traversal, symlink roots or ancestors, symlink upload directories, and changed worktree roots are refused. A generated `.twr-uploads/.gitignore` keeps staged and committed attachments out of git status. A commit checks the declared size, transport SHA-256, and actual disk bytes; verifies that staging directories and the staged file still match their pinned descriptors; syncs the file; and atomically renames it. Upload requests never send prompts or inject bytes into terminals.

The gateway retains its 128 MiB per-device quota over ten minutes, with a minimum charge of 64 KiB per file, including empty files. Each box also enforces that quota for its authenticated caller, limits pending transfers to four per caller and 32 per box, and bounds retained receipts. Cancellation refunds an unfinished reservation and removes its staged file; a committed attachment retains its quota charge and cancellation does not remove the file. Idle transfers and receipts expire after 15 minutes, with periodic cleanup. Pending transfers survive transport reconnects while the gateway, hub, and runner processes remain alive; process restarts discard pending transfer state. The original `File` stays only in application memory, so closing the app before an upload finishes requires selecting it again; an uploaded file stays attached ([above](#thread-attachments)).

Uploads use a bounded lane separate from approvals and other device commands. Client upload calls time out after 15 seconds, gateway requests after 12 seconds and remote runner requests after 10 seconds. After a dropped connection, use Resume to verify the received prefix and continue; the app does not send the file again automatically. An operation already in progress is polled through status. Cancelling a committed transfer reports that its file is kept rather than claiming to delete it. Queued files retain their original workspace and wait while you use another workspace.

Uploaded copies are disposable during explicit park, delete, or manual trim worktree cleanup. Keep an original outside the worktree when you need it later; a captured or generated file may otherwise exist only in the app's memory. Automatic idle trimming does not remove attachments. Configure `park_disposable` if you want different explicit cleanup behavior.

Runner upload commands use four dedicated execution slots and keep their idempotent transfer receipts in the upload manager. Per-chunk results are not added to the runner's ordinary durable command-result spool. File creation, chunk reads/writes, checksum commits, and expired-file cleanup run outside the global upload manager lock.
