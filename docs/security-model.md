# Security model

This page says what twr guarantees, how it enforces each guarantee, and what it does not protect you from. The other pages describe the same rules where they come up; this one puts them together. To report a way around any of them, see [SECURITY.md](../SECURITY.md).

## The trust model

twr starts coding agents (Claude Code, Codex, Grok Build, ACP agents) as your own OS user. An agent can read your files, use your credentials and run programs like anything else you start, within whatever sandbox its runtime applies. twr doesn't change that, and it isn't a sandbox.

What twr adds is a guard on its own controls. Answering a permission prompt or a question, changing a thread's permission mode, deleting threads, emptying or restoring the trash, sending prompts and stopping the hub are yours. The hub refuses all of them to the agents it runs. The orchestrator may send prompts, and may pass on your answers, mode changes and deletions only under the rules below. The guard holds against an agent that uses twr's own channels, the socket and the orchestrator's tools. It can't hold against a process that is indistinguishable from you, and an agent running as your user can start one (see [What twr does not protect against](#what-twr-does-not-protect-against)).

For a repository you don't trust, use the runtime's own sandbox, or run the agents as a separate OS user or in a container. A [runner box](runners.md) can be a container: its agents can't reach the hub's socket at all.

## Who is the user on the hub's socket

Every client (the TUI, the CLI, the orchestrator's MCP server, a script) talks to the hub over one Unix socket. The socket is mode 0600, so only your user can connect (twr creates a missing parent directory at 0700; a directory you name that already exists keeps its own permissions, within the limits in [The socket and the config file](#the-socket-and-the-config-file)). Within your user, the hub decides for each connection, when it opens, whether it comes from you, from the orchestrator or from an agent.

### Agents

A connection is a thread's agent when its process is, or descends from, a process twr started for a thread on this machine: a runtime (a worker's or the orchestrator's), or the CLI of a `twr attach`. The hub matches those processes by pid and start time, so a pid that now names another process matches nothing. Every process twr starts for a thread also carries a `TWR_AGENT` environment variable, which its children inherit, so a background job a worker's shell leaves behind (`nohup cmd &`, reparented to init) still counts. So does a process that clears the variable while one of its parents still has it, and anything that descends from any twr hub or `twr attach`, including another [workspace](workspaces.md)'s. A parent whose environment can't be read counts against the peer (below) only when an agent could have made it unreadable: one that started before the hub, such as a process an agent of an earlier hub left running, or one a privileged daemon started, doesn't, so a process below it that cleared the variable isn't noticed. On macOS a process whose environment is empty counts as one that hid it.

The hub fails closed where it can't tell:

- a peer whose credentials can't be read, or that names no pid the hub can see (another PID namespace), is an agent of no thread;
- a peer whose parent chain can't be read to the end, or whose environment can't be read when it could have hidden it (a process of yours can make itself unreadable to you), is an agent;
- a peer the hub fails to classify for a reason of its own (the read failed inside the hub) is an agent.

The hub's own process, for its in-process clients, is the one exception to the first rule. When the process table can't be read at all, the hub doesn't fail closed (see [What twr does not protect against](#what-twr-does-not-protect-against)).

On macOS, where `ps` doesn't show where one argument ends and the next begins, a hub is recognized only when no part of its arguments before `hub` is a word without a `/` between spaces (a socket path like `/tmp/my home/x.sock` is fine, `/tmp/my files are here/x.sock` is not). On Linux, `/proc` can be mounted with `hidepid`, which hides some of your session's parent processes from you (root's `sshd` or `login`, and the `sshd` process that runs your login). The guard stops at the first parent it can't see and decides by the processes it could read, so your own SSH session still counts as you. With `hidepid`, an agent can also hide one of its own processes this way, and a child of that process that starts again without the variable escapes the guard.

The [notification command](notifications.md) and every [job](usage.md#jobs) carry the marker too, so a `twr` they run counts as an agent.

### What an agent may call

An agent's connection may call only reads and its own thread's jobs: list and read threads, transcripts, events and the control stream, what is waiting on you, the trash's list, usage, the hub's info, a project's standing context, and every thread's jobs and their output. It may start and cancel jobs for its own thread, under the rule in [Jobs](#jobs). Anything else is refused with a message naming the agent's thread. A `twr` command an agent runs gets the same refusal, as does an agent inside `twr attach`.

Reads are not limited to the agent's own thread. Any agent can read every thread's transcript and every job's output.

A connection may hold at most 16 subscriptions (`control.subscribe`, `thread.subscribe`) at once, and the hub serves at most 1024, of which agents' connections together hold at most 256, so an agent can't grow the hub's memory without bound by subscribing again and again, nor take the subscriptions your TUI needs.

### The orchestrator

The hub gives each orchestrator process a fresh token (32 random bytes), passed to its MCP server in a file only you can read and never on a command line or in the runtime's environment. A connection that presents it is the orchestrator, but only when its process descends from the current orchestrator runtime and is still the process that opened the connection; the hub walks the ancestry again at every request. A token presented by any other process, an agent's included, is refused. The orchestrator may call only its own list of methods, described next.

## The orchestrator

The orchestrator is the agent most exposed to text that you didn't write: it reads every worker's reports and replies. twr's guarantees about it don't depend on the model behaving. The hub enforces them.

### What it may do on its own

Through its MCP tools it may start workers (in a configured project, a repository under `project_roots`, or any git repository by absolute path that isn't, and doesn't hold, your home folder, and doesn't hold and isn't inside twr's data directory, `TWR_HOME` or a credentials folder such as `~/.ssh` or `~/.config`), send them prompts, cancel prompts held with `--after`, stop, park, resume and rename them, change a worker's model, move a worker in `plan`, `read-only` or `dontAsk` to another runtime (any other move goes on a confirm card, since runtimes differ in what one mode lets through), write reports, annotate cards, set watches, and read and set a project's standing context (`.twr/context.md`, which goes into every later worker prompt for that project). New workers always start in `[threads] default_mode`, never a mode it picks, and only with a built-in runtime (Claude Code, Codex, Grok Build), a preset you configured, or the project's or default runtime: it never names a command line. It can't attach, stop the hub, switch itself to another runtime, run jobs, empty or restore the trash, or trim.

### The relay rule

Only you answer a permission or a question and change a thread's mode. The orchestrator may relay your answer only in a turn your message started, for an item you could have seen before you wrote, once per item, and only until you send it another message. The hub then reads your message itself: one short command is applied at once, and anything else becomes a confirm card that only you can answer. A lone "yes" never applies at once (you may be answering the orchestrator's own question), and neither does a command that names, or could name, a thread made or renamed after what your screen showed: the orchestrator makes and renames threads without a card, and could otherwise point your words at another thread. A delete it asks for is always a card only you answer. A relay that breaks these rules is refused with `relay_forbidden`. [orchestrator.md](orchestrator.md#the-relay-rule) has the rule in full, including the short-command grammar and messages you take back.

The relay rule covers answers, modes and deletions. It doesn't cover the orchestrator's other tools: an orchestrator misled by a worker's text can still prompt workers that are already in a permissive mode, start new ones in `default_mode`, or write standing context.

### The memory guard

A Claude Code orchestrator runs in `dontAsk` mode with only the twr tools allowed, and its only built-in tools are Read, Write and Edit. A `PreToolUse` hook, `twr claude-memory-guard`, denies any path outside its memory directory, as the file system resolves it, and denies whatever it can't decide. The hub turns off the settings and environment variables it knows can drop or wrap the hook, and gives the orchestrator no file tools at all when managed settings could. It also turns off Claude Code's attachments (`CLAUDE_CODE_DISABLE_ATTACHMENTS`), which would otherwise read a file a prompt names with `@` into the orchestrator's context with no tool call: the hub's notices quote workers' text. Where the confinement ends (a settings `env` block that sets `CLAUDE_CODE_SHELL_PREFIX`, server-managed settings fetched after start, MDM policy), Read reaches anything under its working directory, which is your home directory by default. [orchestrator.md](orchestrator.md#memory) lists these cases. The hook checks a path when the tool is called, so a process of yours (a worker) that swaps a symbolic link between the check and the read can redirect it.

A Codex orchestrator runs in a read-only sandbox with its shell, web, agent, app, browser and image-generation tools turned off, and with no MCP server but twr's: Codex adds the servers twr gives it to those of your Codex config, so the hub reads that config (`config/read`, from the orchestrator's directory, project config included) and turns every other server off by name, turns plugins and apps off, and ends the session if Codex starts a server twr didn't give it, or the config defines one named like twr's. Three built-ins can't be turned off: `apply_patch`, which the read-only sandbox makes fail; `view_image`, which can show it an image file anywhere it can read; and `request_user_input`, which asks you. A Grok Build orchestrator runs with a profile that has no shell, file or web tool. A generic ACP orchestrator keeps its own tools, because ACP can't take them away: it asks you only for the calls it decides need a permission, as its own settings say, and runs the others. Only a Claude Code orchestrator can be attached: the other runtimes' interactive CLIs can't be given these limits on their command line, so the hub refuses.

### Project reads

The orchestrator can read your projects' committed files through the hub, with limits the hub enforces on every runtime ([orchestrator.md](orchestrator.md#reading-your-projects)):

- only configured projects and the projects of existing worker threads, on the hub's machine; never a repository that holds your home folder, twr's data or `TWR_HOME`, or folders such as `~/.ssh` or `~/.config`;
- only the repository's own objects: a git directory outside it, a `commondir`, alternates, or a symbolic link anywhere in its object storage (the objects folder, a loose object's folder or file, a pack) is refused, checked before and again after each read's git commands;
- only git objects at one commit, never the work tree, so untracked and ignored files such as `.env` don't exist for it;
- no transport and no lazy fetch, so a read never downloads; a partial clone isn't read at all;
- files with secret-looking names, or holding a private key or a token of a known format, are refused whole, and a search answers as if they weren't there: it searches again without them, so neither its lines nor its "more matched" depend on them (past 8 such searches it is refused instead);
- at most 40 reads and 256 KB per orchestrator turn, and every read is a line in the conversation.

Limits: the secret filters are heuristics, and a secret under an ordinary name, in a format they don't know, is read like any file. A process that can write the repository's git directory and changes it (alternates, a link in its object storage) and back again while one read's git runs isn't seen; a hard link to another repository's object file isn't told apart from the repository's own. The orchestrator can reach any repository on disk by starting a thread there first, which you see as a new card. Reads work in turns you didn't start, such as a watch firing, so you see them afterwards, not before.

### Text from agents

Whatever reaches the orchestrator as text, a worker's reply quoting a web page or an issue, a file in a repository, a report, can try to make it act. What the hub keeps out of reach whatever the text says: answers, modes, moves to another runtime (but for a thread in a restricted mode) and deletions (above). On Claude Code, Codex and Grok Build, twr also confines the orchestrator's own tools (above): no shell, and no writes outside Claude Code's memory directory, so twr's own secrets (runner tokens in `config.toml`, its MCP token) stay out of its reach, short of the memory guard's gaps and Codex's `view_image` showing it an image file. A generic ACP orchestrator keeps its own shell, file and web tools, and asks you only for the calls it chooses to, so for it only the hub's own refusals hold. What stays reachable is what it may already do: the prompts it sends workers, who usually run in `auto` mode with network access; the reports, notes and standing context it writes; its memory files; and its replies to you, from which you may copy a command.

A file it can read through project reads, a worker of that project could read without asking too. Project reads remove the friction (a new card, the worker's own permission layer), not a boundary.

Two features send agent text on as your prompt, with your authority, and nobody reads it on the way:

- A held prompt's `{report:<thread>}` ([usage.md](usage.md#send-a-prompt-after-another-thread-finishes)) puts one thread's report into another thread's prompt, sent as yours.
- The review loop in [recipes.md](recipes.md#a-review-loop) feeds the reviewer's whole reply to the author as your prompt, round after round.

Use them where you trust both agents' inputs as much as you would trust your own prompt.

A permission card shows what you would allow as the runtime sent it: Claude Code's and Codex's command (or a tool's input), its whitespace as it is, nothing trimmed, and its line breaks as `⏎`. Tabs show as `⇥`. Only printable ASCII, the space, and letters and digits of any script show as themselves; everything else shows as `⟨U+XXXX⟩`: a space at either end, whitespace that only looks like a space (a no-break or thin space), invisible characters such as zero-width or right-to-left marks, combining marks, and symbols and punctuation outside ASCII. So two different commands never read the same. A letter that looks like another one still shows as itself: a Cyrillic `а` in place of a Latin `a` reads the same on the card. The TUI wraps a permission and its whole input without dropping a space at a row's end. So does a directory a Codex approval would also let it write under. A long command is cut on the card, which then says how many characters are left (`… 1234 more characters; open the card to see all`), and the whole command shows as `input:` in the TUI's request popup and in `twr respond`'s output. A command too long even for that (over 64 KiB) can only be denied. A Claude Code card also shows every other field of the tool's input after the command or path, as JSON between `⟦` and `⟧` and marked the same way: a flag that changes what runs, such as `dangerouslyDisableSandbox` (run outside the sandbox), `run_in_background` or `allowed_domains`, a file write's content, an edit's strings, and any field twr doesn't know. Only a Bash call's `description` and `timeout` are left out. Long fields are cut on the card and shown whole as `input:`, and an input over 64 KiB in all can only be denied, a large file write included. The tool's name, and an ACP agent's kind for the call, are marked the same way too. An ACP agent's card shows the agent's own title for the call, which the agent chooses and need not be the command.

## Jobs

A [job](usage.md#jobs) is a command the hub runs for a thread, in its worktree, as the hub's child. It runs outside the runtime's sandbox, with the environment the thread's runtime gets: the hub's environment without twr's tokens, plus `[threads] env` and the project's `env`. So a job can do whatever you can.

- You can start a job for any thread, in any mode.
- A thread's agent can start jobs only for its own thread, only from a process twr started for that thread (a runtime or an attached CLI, or a process that descends from one; the `TWR_AGENT` marker alone isn't enough, so a job can't start jobs), and only while the thread's recorded mode lets it run commands: `manual` or wider. In `plan`, `dontAsk`, `read-only`, or a runtime's own mode id twr can't classify, the hub refuses it.
- The hub checks where a start or a cancel comes from at each request, not only when the connection opened: the process that opened the connection must still be there and still run under its thread's live runtime or attached CLI, its parent chain read twice and confirmed link by link, and the runtime or attach checked again when the request is applied. A process that left them (its parent exited), or that outlived them, still reads but starts and cancels no job. A process left over from an attach that ended doesn't count as the attached CLI, so it can't start jobs on a stopped thread.
- The mode is checked when the job is queued and again right before its command runs, under the same lock as a mode change, so a job still waiting for its slots when the mode narrows doesn't start. A running job isn't stopped when the mode narrows.
- A job an agent started doesn't wake a stopped thread when it ends: the prompt would start the thread's runtime again, with what the job printed.
- The orchestrator runs no jobs. Jobs run only on the hub's own box.
- A thread has at most 8 jobs queued or running. A job has no time limit unless it asks for one.
- Each job records who asked: `user:<client>`, `agent:<thread>` or `attach:<thread>`.

Cancelling, stopping the thread, a forced park or a deletion sends SIGTERM to the job's process group, and SIGKILL 5 seconds later. The hub records the job's process group and its leader's start time before the job's command runs (the job starts as `twr __job-gate`, which runs the command only once the hub lets it, and doesn't when the start time can't be read; on macOS a process the hub starts at the same instant could inherit the hub's end of that gate and let it go early), so if the hub dies, the next hub kills what is left of that group before it records the job lost, whatever its processes' environments say. It checks before each signal that the group is still the job's: its recorded leader still runs, or, with the leader gone, a member the hub saw in it while the job ran (it records them every few seconds) still does. A leaderless group with none of those is left alone and counts as not verified. When it can't verify that nothing of the job still runs (the process table can't be read, or a process survives SIGKILL), it doesn't record the job lost, and the thread starts no runtime and no job until a later start of the hub verifies it. A process the job moves to a session or process group of its own (`setsid`) isn't in that group and outlives the cancel and that cleanup.

Only an agent that can reach the socket can start a job. Codex's sandbox blocks local sockets in every mode but `auto` and the bypass modes; Claude Code has no OS sandbox unless you configure one. If a runtime's sandbox is your boundary, keep its threads from the socket.

## git in repositories agents control

An agent can write the config of the repository it works in, and git's config can name programs for git to run. twr runs git itself (snapshots, worktrees, the trash, merge readiness, project reads), so none of those commands may run a program the repository names:

- **No network.** Every git command runs with `GIT_ALLOW_PROTOCOL` empty and `GIT_NO_LAZY_FETCH=1`: no transport at all (`ext::` included, whatever `protocol.<name>.allow` the repository sets), and no fetch of a partial clone's missing objects. So git itself never runs ssh, a credential helper or a remote helper. Git LFS, a filter of your own config, can (see the limits below).
- **No repository drivers.** Hooks and fsmonitor are off. Before every command that could run a filter, a merge or diff driver, `diff.external` or a hook defined in config, twr lists what the repository's own config defines (its local and worktree config and the files they include, and each initialized submodule's) and overrides each with `-c` so that it runs nothing. When it can't list them all (more than 64 repositories, submodules nested deeper than 4, a driver name with a `=`), the command doesn't run. A new worktree is checked out only once its drivers are off. A file whose merge driver the repository defines counts as conflicting.
- **Work tree pinned.** Work-tree commands name the work tree explicitly, so `core.worktree` can't move them, and variables such as `GIT_DIR` and `GIT_EXTERNAL_DIFF` from the hub's environment are removed.

Limits:

- **Your global and system drivers run.** What your own git config defines is yours and runs on whatever files the repository's attributes give it. Git LFS is one: a checkout twr makes fetches LFS files from the LFS server the repository names, its `.lfsconfig` included, as `git checkout` would. That server can be an `ssh://` URL, and Git LFS then runs your `ssh` (with your `~/.ssh/config` and your agent's keys) to the host the repository chose. Over HTTPS, a server that answers 401 makes Git LFS ask your credential helpers (`git credential fill`) for that host, and a helper with a window may show it. So a repository can make a checkout log in to a host of its choosing as you, with credentials you hold for that host. But Git LFS also runs programs its config names: custom transfer agents, extensions, its askpass, ssh and credential helpers. Where the repository's own config (not `.lfsconfig`, from which Git LFS takes no such key) names any of them, twr turns the LFS filter off for its git commands, as it does a driver the repository names, and logs why once: its checkouts of that repository then hold LFS files as pointers. A repository you set up with its own credential helper, `core.sshCommand` or `core.askPass` is treated the same way. Otherwise LFS repositories keep working. This needs git 2.26 or newer: an older git can't say which config a setting comes from, so twr treats every driver as the repository's and turns your global ones off too, Git LFS's included.
- **The list-then-run race.** The listing and the command are two git processes. Something that can write the config the command reads in between (the repository's `config`, a worktree's `config.worktree` in a repository with `extensions.worktreeConfig`, or a file either includes) can name a driver the listing didn't see, and the command runs it once. An agent that can run what it likes gains nothing from this. A sandboxed one that can write its worktree's git directory (Codex's `auto` mode can) does. twr lists the config again after each such command, where git ran: a driver that appeared without an override, or a different repository found there, is logged as an error naming the directory and the driver. A read (a snapshot, the readiness probe) then fails, so nothing it found is used. A change keeps its result. The next command overrides the new driver. A driver named and removed again between the two listings isn't seen.

[worktrees.md](worktrees.md#what-twrs-git-runs) describes the same from the user's side.

## The trash and trims

Deleting threads, and purging and restoring the trash, are yours: an agent can't ask for them, and the orchestrator's deletion is a card only you answer. A deletion moves a thread's worktree, git's record of it and its branch into the trash, with refs under `refs/twr-trash/<item>/` that keep every commit they reach. It deletes nothing else on the way except the thread's build output. A purge removes only trash items whose manifest names them, and only the refs of that item. twr never removes a worktree by force and never deletes a branch except the one it moves to the trash, with two exceptions for what it made itself and is undoing: a worktree a failed or interrupted thread creation left (removed by force only when its record proves it is that worktree, on the branch twr made for it; that branch goes too, only while its tip is still where twr made it), and one it made while restoring a trash item that failed (checked to be that worktree first) ([worktrees.md](worktrees.md#delete)).

Build output means the git-ignored entries that match `[threads] park_disposable`. Deleting a thread, `twr trim` and the disk card's Trim delete it, and so does an idle trim, which deletes less:

- Only you trim. Agents and the orchestrator can't ask for a trim or answer the disk card.
- A trim deletes only in a linked worktree of the thread's repository that git's record proves is the thread's, on the hub's own box, while the thread takes no turn, runs no job and isn't attached.
- It walks the worktree by directory descriptor and follows no symbolic link it meets. An entry that holds a git repository stays.
- A worktree with a file system mounted inside it is neither trimmed nor deleted. On systems where twr can't list the mount points (anything but Linux and macOS), trims are refused and a deletion moves build output to the trash with the rest.
- An idle trim (`trim_idle_after`, opt-in per project) runs without anyone looking, so it deletes an entry only when one of its path components is named by both `park_disposable` and `idle_trim_disposable`: by default `target/`, `node_modules/`, `__pycache__/`, `.pytest_cache/`, `.mypy_cache/`, `.tox/`, `.gradle/` and `.next/`, never `dist/`, `build/`, `.cache/`, `.venv/` or `coverage/`.

Limits: the deletion is safe against symbolic links and repositories that are there when it runs, not against another process writing into the worktree at the same time (a parent swapped for a link). twr has stopped the thread's runtime by then, but a process of yours, or one the agent left behind, could still write. On macOS twr lists a held directory's entries by path, so a writer that swaps one of its parents meanwhile can make the repository check look elsewhere.

## Remote runners

A runner box connects out to the hub's listener over WebSocket ([runners.md](runners.md)). Hub and runner authenticate each other with the box's token, which never crosses the connection. The runner sends a random nonce, the hub answers with its own and an HMAC-SHA256 of the box and both nonces keyed with the token, and the runner checks that proof before it sends anything else. Then the runner proves the same with its own label, and only then does the hub take its inventory. A proof is bound to its direction and to both nonces, so neither side can replay one.

- The listener is off unless `[hub] listen` is set. The hub refuses a non-loopback address unless it serves TLS (`wss://`) or `allow_insecure_remote = true` says plain text is acceptable. Connections that haven't authenticated yet are limited in number (16, and 4 per address that isn't loopback), in time (15 seconds from the accept for every handshake step together) and in message size (8 KiB). What the hub buffers to send any connection is bounded, so a peer that floods WebSocket pings and reads nothing can't grow its memory, and pings don't keep a silent connection open.
- Something else listening where the runner connects, such as another user's process on a loopback port an `ssh -R` tunnel failed to bind, gets the runner's hello and nothing more, as long as it can't reach the hub's listener itself: no token, no inventory, no way to send it commands. The runner logs that the hub could not prove it knows the token. If that process can reach the hub's listener (a TLS listener open to the network, say), it can relay the handshake: it passes the runner's hello to the hub and the hub's challenge back, and both proofs check out, because they bind the box and the nonces but not the connection they cross. It then sits between the two and can send the runner commands. Use `ssh -o ExitOnForwardFailure=yes`, so a failed forward fails loudly instead, and keep the listener reachable from as few machines as you can.
- The runner connects over plain `ws://` only to a loopback host: `localhost`, an address in `127.0.0.0/8`, `[::1]`, or an IPv4-mapped loopback address such as `[::ffff:127.0.0.1]`. It checks the host as written and resolves no name. Any other host needs `wss://` or `--allow-insecure`. With `wss://` it trusts the public web roots, or only the CA you give it with `--ca`.
- Tokens: neither side sends or logs them, and both check proofs in constant time. The hub answers any peer's hello with a proof, so anyone who can reach the listener can try guesses at a token offline against it: a 256-bit token from `twr runner token` makes that hopeless, a short or guessable one does not. The hub refuses to start with a box token shorter than 16 characters and warns about one shorter than 32. For a box it doesn't know, the hub's proof is random, so a peer can't tell which box names exist. The runner refuses a token shorter than 16, and a token file that other users can access. `twr runner token` prints 32 random bytes in hex. Runtimes never inherit `TWR_RUNNER_TOKEN`.

What a runner can make the hub do: report events for its own box's threads, which the hub checks like a local runtime's (a frame for another box's thread is refused, a replayed one too, and a replayed turn end never releases a queue that a crash holds), so it can raise permission and question cards and write replies and reports for those threads. It lists only its own box's trash: an item whose manifest names another box is left out, and a restore brings back only a thread of the box that holds the item. A second runner with the same token replaces the first. A runner can't call the hub's socket methods.

What the hub can make a runner do: start runtimes, run twr's git operations in the box's repositories, and quiesce a runtime for an attach. Whoever controls the hub can run commands on the box as the runner's user. Posing as the hub takes the token. Without TLS the handshake doesn't protect what follows it, though: someone who can relay and alter the traffic between runner and hub (on a network path, or a loopback port squatted as above while the hub's listener is in reach) can let the handshake through and then send commands. That is why the runner refuses plain `ws://` to anything but loopback. The same goes for remote attach: the hub quotes its command for a POSIX login shell on the box, and a runtime's session id reaches that command from the runner's events. The hub attaches only a session id it would put on a command line, local or remote, whatever the runtime: 1 to 256 letters, digits, `.`, `_`, `:` or `-`, not starting with `-`, so a runner can't hand `claude --resume` an option such as `--dangerously-skip-permissions` for your terminal to run. On an SSH box the remote command runs the box's own twr build (`twr runner --exec`), which looks up the agent's executable on the box the way a spawn does. The arguments and environment still come from the hub, never from the runner's answer, and `--exec` runs only a built-in agent's CLI.

A process on the hub's machine that can read `config.toml` (any agent, since it runs as you) can read a box's token and connect as that runner, on a loopback listener too.

## SSH boxes

An SSH box ([runners.md](runners.md#ssh-boxes)) has no token, no listener and no tunnel. The hub runs ssh to the box itself and speaks the runner protocol over that connection, with the box daemon at the far end.

- **ssh's helpers.** Each ssh the hub runs leads a session and process group of its own, without a controlling terminal. When it ends, what is left in that group (a `ProxyCommand`'s helper, an ssh wrapper's) is killed before ssh is reaped, so the group's id can't name another process yet; a hub that stops kills the groups of the ssh it still runs.
- **ssh.** The hub runs `ssh` (or `TWR_SSH`) with your ssh config and keys, from its own environment, with `BatchMode=yes`, so it never prompts, and with `-o ClearAllForwardings=yes -o ForwardAgent=no -o ForwardX11=no -o PermitLocalCommand=no -o Tunnel=no` before the box's `ssh` words (ssh takes the first value it is given for an option, so these beat your `~/.ssh/config` and any `-F` file) and `-a -x -k` after them (the last of `-a` and `-A` wins, likewise `-x`/`-X`/`-Y` and `-k`/`-K`), so nothing is forwarded: not your ssh agent, X11 display or Kerberos credentials, no port and no tunnel, and no local command runs. The box's `ssh` words may not ask for any of that, share a connection or change what ssh runs or how: such a value is refused when the config is read, by `twr box add`, at hub start and by `box.add`, and by the code that builds every ssh command ([configuration.md](configuration.md#notes-on-some-keys) lists them). The remote command is one string in which every variable part is shell-quoted. `twr box add`, `twr box install` and `twr box doctor` run the same options without `BatchMode` in your terminal, so ssh can ask about the host key or a passphrase, and `twr box login` runs them with a terminal on the box (`-t` instead of `-T`) for the agent's login. `twr attach` to a thread on a box (SSH or token) runs its `ssh -t` with the same forwarding options: an attached agent CLI can't reach your agent either.
- **What ssh prints** is read with limits: the hub reads at most 64 KiB of each of stdout and stderr of a probe, an upload or a cleanup (more fails the attempt and kills that ssh), cuts each line of the relay's stderr at 1 KiB while reading it, and takes at most 1000 such lines per connection as the box's notes, dropping the rest. `twr box add`, `twr box install` and `twr box doctor` read at most 64 KiB of ssh's output. A login script on the box that prints without end can't grow the hub's memory or its log.
- **The hub key.** Each hub instance has an Ed25519 key, `box-key` in its data directory (PKCS#8, mode 0600; the hub refuses one other users can access). The hub passes its public key to the relay on the ssh command line. The private key never leaves the hub's machine.
- **The sealed channel.** The daemon opens with a hello line: its box, a random nonce, an ephemeral X25519 key and its build. The hub answers with its own nonce and ephemeral key and an Ed25519 signature, made with the hub key, over a transcript of the channel's version, the box, both nonces, both ephemeral keys and the hub's public key. The daemon checks it against the hub key it was started with. Both sides derive one ChaCha20-Poly1305 key per direction (X25519, then HKDF-SHA256 over the transcript) and exchange records of at most 64 KiB with counter nonces that never wrap; any failure ends the channel. The runner protocol runs inside, unchanged. The relay, the daemon's socket and ssh carry only those records.
- **The daemon's socket** is in a 0700 directory, mode 0600, and the daemon drops a peer that doesn't run as its user. Its data directory is 0700.
- **The builds tree.** Before it runs or uploads anything, the hub's probe checks `<data>/twr/runner/builds` on the box: it, `<data>/twr/runner` and `<data>/twr` must be your directories, not symbolic links, that neither group nor others can write to, and every directory above them must be yours or root's and not writable by every user unless it has the sticky bit (as for the hub's own directories, a directory its group may write to passes). A symbolic link on the way must be yours or root's, and the directories above where it points are checked the same way. A data directory whose path holds a control character is refused too (it could split the probe's lines), and so is a path whose owner and mode can't be read. A builds tree that fails is not used at all: the box shows `needs_install` with the path and why, and `twr box add` and `twr box install` refuse it. A build whose directory or executable fails the same check (a symbolic link, one others can write to) is not run; the box's notes name it. Every upload and install script checks the tree again on the box before it writes, and the relay checks it before it records its build. Otherwise another user, with `XDG_DATA_HOME` on shared storage say, could put a program where the hub runs one, or replace an upload after its checks. A directory of another user that root put there is refused like any other.
- **Uploads.** The hub uploads only its own executable. `twr box install` uploads a file you name with `--binary`, or a release archive whose `sha256sums.txt` signature verified with the release key and whose SHA-256 matches it, as `twr update` checks a release. On the box, the upload goes to a temporary file under the builds directory (umask 077), and its size, its SHA-256 (when the box has `sha256sum` or `shasum`) and its `--version` are checked before it is moved into place; a mismatch removes it, and so does a `sha256sum` or `shasum` that is there but fails or prints no digest (only a box with neither falls back to size and version, and a release install needs one).
- **systemd-run.** When the relay starts the daemon as a transient user service, it passes its environment on by name (`--setenv=NAME`, which takes the value from `systemd-run`'s own environment), so no value appears on a command line other users can read, and turns the service manager's `$VAR` expansion off (`--expand-environment=no`), so the paths the relay resolved reach the daemon as they are (a `systemd-run` too old for that option fails, and the relay starts the daemon in a new session instead). It leaves out `SSH_CONNECTION`, `SSH_CLIENT`, `SSH_TTY`, `SSH_ORIGINAL_COMMAND` and `TWR_RUNNER_TOKEN`.
- **launchd (a Mac).** The relay starts the daemon as a launchd job in your GUI session (`launchctl bootstrap gui/<uid>`), so the daemon and its agents run in that session, where the login keychain can be read ([runners.md](runners.md#mac-boxes)). The job's plist holds the daemon's command line and an allowlist of the relay's environment only (`PATH`, `HOME`, `SHELL`, `USER`, `LOGNAME`, `LANG`, `LC_*`, `TMPDIR`, `TZ`, `XDG_*`, `TWR_CLAUDE_BIN`, `TWR_CODEX_BIN`, `TWR_GROK_BIN`, `TWR_BOX_PROBE`, `TWR_AGENT_PROBE`), so no secret is written to disk: an API key in the ssh session's environment doesn't reach the daemon. The plist is created exclusively, mode 0600, in the daemon's 0700 data directory, and deleted right after the bootstrap, whatever happened (launchd keeps the job's definition); one a relay killed part way left behind is removed by the next relay that tries launchd to start the daemon (also when it then starts it from ssh), not by one that `TWR_BOX_LAUNCHER=setsid` makes start it in a session of its own. Between writing and deleting it, a process of your user could read it, as it could read the relay's environment. Each start uses a new label (`tools.twr.box.<hash>.<random>`), and a relay boots out only jobs of its own hub key and box that launchd says are loaded but not running.

What a process of your user on the box can do: kill the daemon or its agents; ask the daemon to stop; listen where the daemon's socket goes while no daemon runs, and so pose as the box's runner to the hub, with what a runner can make the hub do (above). What it can't: read or change what passes between the hub and the genuine daemon, or pose as the hub to the daemon, which takes the hub's private key. Whoever controls the hub, or the hub's machine as you, can run commands on the box as your user, as with a token runner.

Residuals: a hub started without access to your ssh-agent can't connect, and a hub that has it can use every key in it for the box's host; the build the hub launches is checked by hash only when the box has `sha256sum` or `shasum` (size and version otherwise); and two hubs on different machines that share a repository on a box can collide on branch names.

## The socket and the config file

The hub's socket is mode 0600; twr creates a missing parent directory at 0700, and an existing one you named (`--socket`, `hub.socket`) keeps its permissions. The hub sets the socket up by path (it binds it in a private directory there, then links it into place), so it refuses a parent directory another user owns (root aside) or one every user may write to without the sticky bit (`/tmp` has it), where another user could swap those entries; one its group may write to (a umask of `002` makes such directories, usually with a group of your own) is used and logged as a warning. The data directory, with `twr.db`, `hub.log`, job logs, the trash and the orchestrator's MCP configuration (which names the command its runtime starts), is kept at 0700: twr refuses to start with a data directory another user owns, or one it can't make 0700, since that user could replace what twr keeps there. For the data directory and the socket's directory, every directory their paths go through as the system resolves them, including the directory of each symbolic link on the way, must be yours or root's and not writable by every user unless it has the sticky bit, and each symbolic link must be yours or root's, as OpenSSH requires of its files' paths; a directory its group may write to is logged. Every client checks that the process listening on the socket runs as its own user (`SO_PEERCRED` on Linux, `getpeereid` on macOS) and refuses it otherwise, so a socket another user put at a path in a shared directory (`--socket`, `hub.socket`, `TWR_HOME`) is never used. The hub has no TCP listener for clients; the runner listener speaks only the runner protocol.

`config.toml` can hold secrets: box tokens, a `[notify]` command with a webhook URL, `env` values. When a config holding a box token or a `[notify]` command has any group or other permission bit, the hub warns at start, in its log and in `twr info`, with the `chmod 600` to run. It doesn't refuse to start. The orchestrator's `show_config` never shows a token, an `env` value, a preset's command line, a box's `ssh` destination or the TLS files. An agent can't call it, but can read `config.toml` directly.

## Releases and updates

Each release's `sha256sums.txt` (the SHA-256 checksums of the archives and of `install.sh`, after a line naming the release, `# twr release <tag>`) and its `install.sh` are signed with an Ed25519 key. The private key is a secret of the release workflow's `release` environment, and the workflow checks the signatures against the committed public key, [`release/signing-key.pub`](../release/signing-key.pub), before it publishes.

- **`twr update`** picks one release (`--version`, else the latest on GitHub), downloads its `install.sh`, `sha256sums.txt` and their signatures over HTTPS, and checks both signatures with the key built into twr. Nothing runs unless both verify, the checksums name the release it asked for, and they list that `install.sh`. So the signed files of another release, an older one with a known hole say, or one release's installer with another's checksums, are refused. It then runs that `install.sh` with the checksums it verified, for that release, so the archive must match them. A missing signature stops it like a bad one: every release is signed. With `TWR_INSTALL_SCRIPT_URL` (a mirror), the installer's signature, the checksums and the archive come from the mirror's directory and are checked the same way; without `--version`, the release the checksums name is the one installed. A `file://` mirror's files are read only when they are regular files, at most 1 MiB each and within 60 seconds, as downloads are: a FIFO or a device there fails the update instead of hanging it or filling memory.
- **`install.sh`** checks `sha256sums.txt.sig` when the `openssl` on the machine can verify Ed25519 signatures (OpenSSL 3.0 or newer), which it tests first on a signature built into the script. Then a missing or bad signature stops the install, and nothing turns that off. Checksums that name another release than the `TWR_VERSION` asked for stop it too. Without such an `openssl` (macOS ships LibreSSL), it warns that the checksums were not signature-checked and goes on; `TWR_REQUIRE_SIGNATURE=1` makes that fatal. With `TWR_SHA256SUMS_FILE`, which `twr update` sets, the script checks no signature: the caller has verified the file. Its curl downloads use HTTPS only, TLS 1.2 or newer, except from a `TWR_DOWNLOAD_URL` you give; wget, used when there is no curl, gets no such options.
- **A first install** with `curl -fsSL https://twr.tools/install.sh | sh` trusts twr.tools, which serves `install.sh` from the repository's `main` branch: nothing has checked the script before it runs. To check it first, download `install.sh` and `install.sh.sig` from the release and verify them as [install.md](install.md#checking-the-signature) shows, then run that file.

Limit: `install.sh` stages the new binary in the install directory before renaming it into place. In an install directory that other users can write to and that has no sticky bit, another user could interfere with that file. The default, `~/.local/bin`, is yours alone.

## Debug builds

The test suite runs inside twr threads, where its hubs and clients would count as that thread's agent. So a build with debug assertions (`cargo build` without `--release`, `cargo install --debug`) trusts `TWR_TEST_USER_TOKEN_FILE`: a client that presents the token in that file counts as the user of a hub started with it under `TWR_HOME`. The hub trusts the file only when it is a regular file owned by the hub's user with no group or other access, and agents' processes never inherit the variable. Such a build also lets `TWR_TEST_RELEASE_KEY_FILE` replace the release key for `twr update`. Release builds ignore both, and clients built for release never send the token: the installer, the release archives and `cargo install` all install release builds. Don't use a debug build of twr as your everyday twr.

## What twr does not protect against

- **Processes that look like you.** Some programs you already run start commands when asked: your tmux server (a new window), a `screen` session, `systemd-run --user`, `ssh localhost`, an IDE's or editor's remote server, `at` and `cron`. A command an agent gets one of them to start has that program's parents and environment, which are yours. twr can't tell it from something you ran, and it gets your authority on the socket: answering permissions, changing modes, starting jobs for any thread. So does a process that both starts itself again without `TWR_AGENT` and leaves its parent, and, with `/proc` mounted `hidepid`, a process an agent starts without the marker below one it made unreadable.
- **A process table twr can't read.** When the hub can't read the process table at all (`ps` failing on macOS, no `/proc` on Linux), a peer counts as you, unless its environment can be read and carries the marker. The hub logs it. Failing closed there would lock you out of your own hub. On macOS the hub reads the process table, and the environments it checks for the marker, by running `/bin/ps`, and a process of yours, an agent's included, can make those runs fail (by stopping or killing them): there an agent can bring this about on purpose. It gains what the first item already gives it. Reading the process table in-process on macOS is planned.
- **Processes that can trace yours.** Where one process of yours may attach to another (`ptrace`, `/proc/<pid>/mem`, `pidfd_getfd`; Linux with `kernel.yama.ptrace_scope` at 0), an agent's process can act through a connection the hub already judged to be you: the TUI's, a CLI's, or the hub's own. Set `kernel.yama.ptrace_scope` to 1 or higher (Ubuntu's default), which limits tracing to a process's own descendants.
- **pid reuse.** The hub identifies a peer by the pid its credentials name when it connects, not by a handle on the process. A peer that exits and whose pid another process takes before the hub has read it could be judged as that process. With today's pid ranges that isn't practical.
- **Reading what twr records.** Every agent can read every thread's transcript, every job's output and the control stream through the socket, and `twr.db`, `hub.log`, job logs and the trash directly from disk. Prompts, replies and tool output are not secret from your agents.
- **The hub's environment.** Runtimes, jobs and the notification command inherit the hub's environment, without twr's own tokens: API keys, cloud credentials and `SSH_AUTH_SOCK` in it reach every agent. A hub started from a shell (an agent's included, when none was running) passes that shell's environment, `PATH` and `TWR_*_BIN` included, to everything it starts.
- **Files a runtime reads at start.** A permission mode bounds one session of a runtime. An agent in a mode that lets it change its worktree without asking can change files its runtime reads the next time it starts there, and so widen its next session: Claude Code's `.claude/settings.local.json` (hooks, allow rules), a subagent's `permissionMode`, Codex's `.codex/config.toml`, its instructions (`CLAUDE.md`, `AGENTS.md`). twr passes its own settings to the orchestrator, not to workers.
- **What a repository brings with it.** What a repository commits applies in every twr mode, which doesn't bound it: Claude Code's `.claude/settings.json` hooks and allow rules, the servers of its `.mcp.json` (with `enableAllProjectMcpServers`), Codex's `.codex/config.toml`. A worker in a repository runs what the repository's settings say, as its build does. Give threads only repositories you'd build. The orchestrator can start a worker in any git repository outside the folders it is refused (not only your configured projects), without asking you.
- **The runtimes' own behaviour.** Each runtime's sandbox, permission modes and what it runs without asking are its own: Grok Build 1.0.44, for example, runs some shell commands it deems safe without asking, even in `default` mode ([runtimes.md](runtimes.md#permission-modes)). Report a problem there to its vendor.
- **Global git drivers and the list-then-run race**, described in [git in repositories agents control](#git-in-repositories-agents-control).
- **Debug builds**, described in [Debug builds](#debug-builds).
- **Your account and `config.toml`.** Anyone who controls your user account, or can write your `config.toml`, controls twr.
